# Incident catalogue: distributed systems

Real, publicly documented production incidents and engineering analyses covering consensus, coordination services, queues and streaming, retries and retry storms, cascading failures, deploys and config pushes, Kubernetes, cloud region outages and observability failures. Each source is primary: the company's own postmortem, status page or engineering blog, an official regulator report, or a Jepsen analysis. Every URL was opened and checked against the summary in October 2026. Summaries are in our own words. Numbers come from the source; where a source leaves something out, so does the entry.

Problem-shape vocabulary: contention, duplicates, ordering, fan-out, hot spots, overload, partial failure, multi-step consistency, finding things fast, trust but verify.

## Consensus, leader election and failover

- **GitHub, 2012-09: Pacemaker split brain on the MySQL cluster** — Heavy migration load failed a health check, so Pacemaker moved the active MySQL role to a node with a cold buffer pool. That node performed badly and triggered another failover. The next day a Pacemaker segfault partitioned the cluster, and two nodes each elected themselves master. Over two days there was 1h46m of downtime plus about an hour of degradation. Because MySQL and Redis IDs drifted apart, 16 private repos were visible to non-collaborators for 7 minutes. Afterward, automatic failover of the active role needed a human to start it, and they audited the Pacemaker/Heartbeat stack. Tags: [partial failure, multi-step consistency, trust but verify] [topics: mysql, pacemaker, split-brain, failover]. Source: https://github.blog/news-insights/the-library/github-availability-this-week/
- **GitHub, 2018-10: 43-second partition causes a 24-hour degradation** — Optical equipment maintenance cut the US East hub off from the primary data center for 43 seconds. In that window, Orchestrator used Raft to promote West Coast MySQL primaries. Writes then landed on both coasts, so a clean failback was impossible. GitHub restored from backups and replayed data, and service was degraded for 24h11m. At the peak, more than 5M webhook events and 80k Pages builds were backlogged, about 200k webhook payloads expired, and one cluster had 954 unreplicated writes to reconcile. Fixes: Orchestrator can no longer promote across regions, they moved toward active/active/active serving, and they invested in chaos testing. Tags: [partial failure, multi-step consistency, ordering] [topics: mysql, raft, orchestrator, failover, webhooks]. Source: https://github.blog/news-insights/company-news/oct21-post-incident-analysis/
- **Stripe, 2019-07: shard can't elect a primary, and the rollback makes it worse** — A database minor-version upgrade carried a failover bug that only showed when several nodes stalled. One shard could not elect a new primary, and because the API depended on that shard, API compute starved. Rolling back the election protocol then clashed with a recent config setting and caused CPU starvation. Most API requests failed in two windows, of 27 and 93 minutes. Fixes: monitoring for nodes that stop reporting replication lag, circuit breakers so one shard can't take down the whole API, and limits on client retries. Tags: [partial failure, overload, trust but verify] [topics: database, leader-election, circuit-breaker, rollback]. Source: https://stripe.com/rcas/2019-07-10
- **Cloudflare, 2020-11: degraded switch confuses etcd, which triggers DB failover** — A switch failed partially: its control-plane protocols stayed up while it dropped data-plane packets. etcd nodes disagreed about who could reach whom, leader elections kept tying, and the cluster went read-only. The database manager relied on etcd, so it promoted a replica. A bug then forced every replica to be rebuilt, which left one primary overloaded. Over 6h33m the API success rate fell as low as 75% and the dashboard ran up to 80x slower, while the edge network was unaffected. Fixes: the replica-rebuild bug, slower auto-promotion, and sessions that work across data centers. Tags: [partial failure, overload, trust but verify] [topics: etcd, raft, postgres, failover, network]. Source: https://blog.cloudflare.com/a-byzantine-failure-in-the-real-world/
- **Google Cloud, 2020-12: quota automation starves the Paxos leader behind Google login** — During a migration to a new quota system, legacy components reported the User ID Service's usage as zero. When a grace period ran out, automation cut the account database's quota. The Paxos leader could no longer write, reads went stale, and authentication failed. For about 47 minutes nearly all authenticated traffic returned 5xx, including all Workspace apps; BigQuery streaming saw about 75% errors. Fixes: quota changes can no longer go global quickly, monitoring for bad configs, and better write resilience in the identity database. Tags: [trust but verify, partial failure] [topics: paxos, quotas, authentication, automation]. Source: https://status.cloud.google.com/incident/zall/20013

## Coordination services and service discovery

- **Discord, 2017-10: Redis failover turns into a full real-time restart** — A Google Cloud live migration knocked a Redis primary offline. The Redis cluster failed over correctly, but API instances hit a known bug in handling the failover. After that, a bad edge-cache rule, a Cassandra failure, out-of-memory guild and session nodes, a push-system failure and a misset reconnect setting piled on. The outage lasted about 2h51m and ended with a full restart that reconnected millions of clients over about 20 minutes. Discord fixed the failover bug, changed the cached route, and added early-warning monitoring. Tags: [partial failure, overload, fan-out] [topics: redis, failover, cascading-failure, reconnect-storm]. Source: https://discordstatus.com/incidents/qk9cdgnqnhcn
- **Discord, 2020-03: empty etcd value crash-loops service discovery** — A new API node's announce request was cut off after its headers but before its body. etcd's v2 API did not check the body against Content-Length and stored an empty value. Elixir watchers crashed parsing it, and their supervisors hit restart limits and took down whole nodes, about 50% of watchers across clusters. Discord was down for most users for about 74 minutes, and recovery needed throttled reconnects. Fixes: announces are sent in a single packet, and watchers skip corrupt entries instead of crashing. Tags: [trust but verify, fan-out, partial failure] [topics: etcd, service-discovery, elixir, input-validation]. Source: https://discordstatus.com/incidents/62gt9cgjwdgf
- **Roblox, 2021-10: 73-hour outage from Consul contention** — Roblox enabled Consul's new streaming feature on a high-traffic service. Under heavy load it caused contention on a single Go channel. Separately, BoltDB's freelist bloat made Raft writes and leader elections slow: the log was 4.2GB with only 489MB live. Every backend service shared that one Consul cluster, and monitoring depended on it too. The platform was down for 73 hours for about 50M daily players. Fixes: dedicated Consul clusters per critical service, telemetry with no Consul dependency, a move to bbolt, and multi-AZ infrastructure. Tags: [contention, hot spots, finding things fast] [topics: consul, raft, boltdb, service-discovery, observability]. Source: https://about.roblox.com/newsroom/2022/01/roblox-return-to-service-10-28-10-31-2021
- **Slack, 2022-02: Consul agent rollout empties the cache, and a scatter query melts the DB** — A Consul agent upgrade rolled out to 25% of the fleet. Restarting agents deregistered memcached nodes, which were then replaced with empty caches. On a cache miss, client boot ran a scatter query across every shard, so database load grew faster than linearly with misses. Timeouts stopped the cache from refilling, and client retries locked in the cascade. Fixes: boot requests were throttled and limits raised step by step, the query moved to a table sharded by channel, and the Consul rollout process and Mcrib control loop were changed. Tags: [fan-out, overload, hot spots] [topics: consul, memcached, cache-stampede, retries, sharding]. Source: https://slack.engineering/slacks-incident-on-2-22-22/
- **AWS, 2025-10: DNS automation race leaves DynamoDB's endpoint with no IPs** — In DynamoDB's DNS system, a slow DNS Enactor applied an old plan over a newer one, because its staleness check had gone out of date while it waited. Another Enactor's cleanup then deleted that old plan, which left dynamodb.us-east-1 with an empty record. DynamoDB errors lasted about 2h52m. EC2's lease manager depended on DynamoDB and went into congestive collapse, and NLB health checks removed capacity, so the event ran about 14.5 hours in total. The automation was disabled worldwide until the race is fixed. NLB gets velocity limits on failover, and EC2 gets throttling based on queue size. Tags: [ordering, multi-step consistency, overload] [topics: dns, dynamodb, race-condition, us-east-1]. Source: https://aws.amazon.com/message/101925/

## Queues, streaming and message brokers (Jepsen and incidents)

- **Jepsen (Kafka 0.8), 2013-09: in-sync replica set shrinks to just the leader** — When the ISR shrank to only the leader, that leader acknowledged writes that existed only on its own disk. ZooKeeper could then elect a lagging replica as the new leader. In one run, 520 of 987 acknowledged writes (about 53%) were lost. The analysis recommended keeping the ISR at a majority or more, and blocking instead of silently dropping data when it empties. Kafka later added min-ISR and a setting to turn off unclean leader election. Tags: [partial failure, trust but verify, ordering] [topics: kafka, zookeeper, replication, data-loss]. Source: https://aphyr.com/posts/293-call-me-maybe-kafka
- **Jepsen (RabbitMQ), 2014-06: mirrored queues drop acknowledged messages** — Under random network partitions, a node that rejoined threw away its own queue state and took the primary's, even with publisher confirms and pause_minority set. About 35% of acknowledged enqueues were lost (1,312 messages), and there were 24 duplicate deliveries. A lock built on RabbitMQ also let two holders in at once. The analysis says not to use RabbitMQ as a lock, and to prefer manual reconciliation or federation over automatic partition handling. Tags: [duplicates, partial failure, trust but verify] [topics: rabbitmq, queues, locks, partitions]. Source: https://aphyr.com/posts/315-call-me-maybe-rabbitmq
- **Jepsen (etcd 3.4.3), 2020-01: key-value ops are safe, locks are not** — Key-value operations, including multi-key transactions, were strict serializable under every fault tested. Locks, however, did not guarantee mutual exclusion even on healthy clusters, and in one test about 18% of acknowledged updates to a lock-guarded set were lost. etcd also skipped re-checking lease validity before granting a lock it had been waiting for. The fix is fencing tokens, such as the lock key's revision, or transactions that check the lock. etcd updated its documentation on guarantees. Tags: [contention, trust but verify] [topics: etcd, distributed-locks, fencing, leases]. Source: https://jepsen.io/analyses/etcd-3.4.3
- **Jepsen (Redpanda 21.10.1), 2022-04: duplicates, inconsistent offsets and lost messages** — Server-side idempotence was off by default, so producer retries wrote duplicates, and duplicates still happened with it on. Uncommitted Raft entries were applied too early, so messages were reordered or ended up at more than one offset. Some acknowledged messages never showed up in any poll. Transactions allowed aborted reads. Most issues were fixed by 21.11.15, and idempotence was planned to be on by default in 22.1.1. Tags: [duplicates, ordering, multi-step consistency] [topics: kafka-api, redpanda, raft, idempotence, transactions]. Source: https://jepsen.io/analyses/redpanda-21.10.1
- **AWS, 2020-11: Kinesis capacity add hits the OS thread limit** — On every front-end server, the thread count grows with the size of the fleet, so adding capacity pushed every server past the OS thread limit. Shard-map caches failed to build, so requests could not be routed. Kinesis was impaired for about 17 hours. Cognito, CloudWatch, Lambda, autoscaling and EventBridge were hit too, and so was the Service Health Dashboard. Fixes: fewer, larger servers, alarms on thread use, a separate cache fleet, and faster cellularization. Tags: [fan-out, overload, finding things fast] [topics: kinesis, streaming, thread-limits, cells]. Source: https://aws.amazon.com/message/11201/
- **Honeycomb, 2025-12: Kafka loses redundancy and tiered storage blocks recovery** — The EU Kafka cluster lost redundancy, and about a quarter of event partitions had no leader. Unbalanced brokers then filled their disks, and ingest was switched off with under 5% disk left. Turning off tiered storage freed space but made damage to internal metadata permanent, and the cluster's control plane later locked up. Customers saw about 6h of full ingest outage, about 18h of SLO processing delay, and about 4 days of lost Activity Log data. The team rehearsed and ran a full evacuation to a new cluster, moving producers first and then consumers. Tags: [partial failure, hot spots, multi-step consistency] [topics: kafka, tiered-storage, disk-exhaustion, migration]. Source: https://status.honeycomb.io/incidents/pjzh0mtqw3vt

## Retries, retry storms and cascading failures

- **AWS, 2011-04: EBS re-mirroring storm** — A network change done wrong sent traffic onto the low-capacity backup network and cut EBS nodes off from each other. When they came back, they all searched for space to re-mirror at once. That used up the cluster's capacity, and aggressive retries plus a race condition kept volumes stuck. At the peak, about 13% of volumes in the zone were stuck. Slow API calls drained the regional control plane's thread pool, the event lasted about three days, and 0.07% of volumes could not be restored. Fixes: retries back off and reconnect to their old replicas, AZ-aware load shedding, and per-cluster control-plane functions. Tags: [overload, fan-out, partial failure] [topics: ebs, retries, backoff, control-plane]. Source: https://aws.amazon.com/message/65648/
- **Microsoft Azure, 2012-02: leap-day certificate bug spread by self-healing** — The guest agent set certificate expiry to the current date plus one year, which gave 29 Feb 2013, an invalid date, so the agent failed to start. After three timeouts the host agent marked the server as faulty hardware, and service healing moved its VMs to other servers, where the same bug fired. A rushed fix then pushed an incompatible host agent to seven clusters, which took VMs off the network. Compute had a partial outage for about 10 hours, and service management was turned off worldwide. Fixes: date-bug analysis, telling software faults from hardware faults, failing fast, and a 33% credit. Tags: [fan-out, trust but verify] [topics: time, certificates, self-healing, deploys]. Source: https://azure.microsoft.com/en-us/blog/summary-of-windows-azure-service-disruption-on-feb-29th-2012/
- **AWS, 2021-12: internal network congestion and retries without backoff** — An automated scaling action set off a surge of connections from many internal clients, which overwhelmed the devices between AWS's internal and main networks. A latent bug kept clients from backing off, so their retries sustained the congestion. Monitoring and deploy tooling ran on the same internal network and degraded too. Recovery took about 7 hours, with Route 53 APIs, the console, EC2 launches and EventBridge impaired. Fixes: a fix for client backoff, protective network configuration, and a new multi-region health dashboard. Tags: [overload, finding things fast] [topics: retries, backoff, network, us-east-1, observability]. Source: https://aws.amazon.com/message/12721/
- **Google Cloud, 2025-06: null pointer in Service Control causes a global crash loop and a thundering herd** — A new quota-policy check had no error handling and no feature flag. A policy row with blank fields replicated worldwide within seconds and crashed Service Control in every region. When tasks restarted in us-central1, they overloaded Spanner because there was no randomized backoff. External APIs returned 503s for hours. us-central1 took about 2h40m to recover, and the status page lists dozens of affected products. Fixes: fail-open checks, feature flags required for critical changes, incremental rollout of global data, and randomized exponential backoff. Tags: [trust but verify, overload, fan-out] [topics: config-push, spanner, backoff, feature-flags]. Source: https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW
- **Discord, 2026-03: pod scale-down sets off reconnect and voice-syncer storms** — A config change to make session pods larger halved their number in one zone. Pods were terminated before they could hand off, so 17% of sessions ended ungracefully. Reconnects hit an untuned rate limit and ran gateways out of memory. Two single-process Erlang supervisors became bottlenecks, which blocked etcd heartbeats and dropped instances from the hash ring. Voice and video were mostly down for about 3h17m. Fixes: an admission webhook that blocks scale-down until pods drain, partitioned connection pools, and retuned rate limits. Tags: [overload, contention, fan-out] [topics: kubernetes, elixir, rate-limiting, etcd, reconnect-storm]. Source: https://discord.com/blog/behind-the-scenes-of-the-3-25-26-voice-outage

## Deploys and config pushes

- **Knight Capital, 2012-08: one server missed the deploy and dead code ran** — A technician copied new order-routing code to only seven of eight servers. The new code reused a flag that once switched on the retired "Power Peg" logic, so the eighth server ran that defunct code and sent orders without stopping. Uninstalling the new code from the other seven made things worse, because they then ran Power Peg too. In about 45 minutes Knight got over 4M executions in 154 stocks and lost more than $460M. The SEC found there was no second-person review of the deploy and no written procedure, and that 97 warning emails went unacted on. Tags: [trust but verify, multi-step consistency, finding things fast] [topics: deploys, feature-flags, dead-code, rollback]. Source: https://www.sec.gov/litigation/admin/2013/34-70694.pdf
- **Google Cloud, 2016-04: canary flagged a bad config but the rollout continued** — Removing an unused IP block left a second config file out of sync, and a bug made the config system drop every GCE IP block. The canary caught the problem, but a second bug kept that result from stopping the push. The progressive rollout withdrew announcements site by site until GCE had no external connectivity for about 18 minutes, with inbound traffic down more than 95%. Fixes: before/after checks on route announcements, semantic config checks, and 14 engineering changes. Credits were 10% for GCE and 25% for VPN. Tags: [trust but verify, partial failure] [topics: config-push, canary, bgp, networking]. Source: https://status.cloud.google.com/incident/compute/16007
- **Cloudflare, 2019-07: WAF regex pushed globally pegs every CPU** — A new XSS rule's regex backtracked catastrophically. It went out to the whole network in seconds through Quicksilver, because WAF rules skipped staged rollout. A CPU safeguard had been removed by accident in an earlier refactor. About 80% of traffic was lost for 27 minutes, with 502s everywhere and the dashboard and API down too. Fixes: they restored the safeguard, reviewed all 3,868 rules, added CPU profiling to tests, moved toward RE2 or the Rust regex engine, and added staged rollouts for rules. Tags: [trust but verify, overload] [topics: config-push, regex, waf, staged-rollout]. Source: https://blog.cloudflare.com/details-of-the-cloudflare-outage-on-july-2-2019/
- **Cloudflare, 2020-07: one-line router edit pulls traffic into Atlanta** — During congestion work, an edit to the Atlanta router's config removed a prefix-list condition instead of turning off a term. Atlanta then advertised all its routes across the backbone with a higher local-preference than local routes, and traffic from about 20 locations converged on one router. Network traffic fell by about 50% for 27 minutes. Fixes: maximum-prefix limits on backbone sessions and a local-preference change so one site can't attract others' traffic. Tags: [hot spots, overload] [topics: bgp, config-change, backbone]. Source: https://blog.cloudflare.com/cloudflare-outage-on-july-17-2020/
- **Fastly, 2021-06: valid customer config triggers a latent bug** — A May 12 deploy shipped a bug that only fired with one specific combination of customer config settings. On June 8 a customer pushed a valid config with that combination, and 85% of Fastly's network returned errors. Monitoring caught it within a minute, and 95% of the network was back within 49 minutes. A permanent fix rolled out the same day, along with a review of why QA missed the bug. Tags: [trust but verify, fan-out] [topics: cdn, config-push, latent-bug]. Source: https://www.fastly.com/blog/summary-of-june-8-outage
- **Meta (Facebook), 2021-10: backbone command takes everything offline, then DNS withdraws itself** — A maintenance command meant to check backbone capacity disconnected every backbone link, and a bug in the audit tool failed to block it. DNS servers that could no longer reach the data centers withdrew their BGP routes, so the outside world could not resolve Facebook's domains. Remote tools depended on the same DNS, and physical security slowed onsite access. The post gives no user-impact figures. During recovery, power use swung by tens of megawatts, and Meta planned drills that simulate a global backbone loss. Tags: [partial failure, finding things fast, trust but verify] [topics: bgp, dns, backbone, out-of-band-access]. Source: https://engineering.fb.com/2021/10/05/networking-traffic/outage-details/
- **Cloudflare, 2022-06: reordered BGP policy withdraws prefixes at 19 sites** — A change to spine router policy moved a reject-all term ahead of the terms that advertise site-local prefixes. The 19 affected data centers were about 4% of the network but carried about 50% of HTTP requests. The internal load balancer also depended on those prefixes, so small clusters received full-size load. The outage lasted about 1h15m. Fixes: test procedures specific to these data centers, a redesigned policy structure, and automatic commit-confirm rollback. Tags: [trust but verify, hot spots] [topics: bgp, config-change, staged-rollout]. Source: https://blog.cloudflare.com/cloudflare-outage-on-june-21-2022/
- **CrowdStrike, 2024-07: content update reads input 21 of 20** — A new template type defined 21 input fields, but the sensor code passed only 20. Earlier template instances used a wildcard for field 21, so the mismatch never surfaced. On July 19 a channel file used a real match criterion on field 21, and the Content Interpreter read past the end of the array, crashing Windows hosts. The content validator had a logic error that let it through, and the file reached every sensor at once. Fixes: runtime bounds checks, a compile-time check on input count, more template testing, and staged canary deployment of template instances. Tags: [trust but verify, fan-out] [topics: config-push, bounds-checking, staged-rollout]. Source: https://www.crowdstrike.com/wp-content/uploads/2024/08/Channel-File-291-Incident-Root-Cause-Analysis-08.06.2024.pdf
- **Cloudflare, 2025-11: permissions change doubles a feature file and proxies panic** — A ClickHouse permissions change made a metadata query return duplicate columns. That doubled the Bot Management feature file, which is rebuilt every five minutes and pushed network-wide. The file went past a 200-feature preallocated limit, and an unhandled Rust unwrap panicked and returned 5xx. Because only some database nodes produced the bad file, the network flapped between working and failing, which first looked like a DDoS. Core traffic was largely failing for about 3 hours. Fixes: treat internal config like user input, add global kill switches, and stop core dumps from swamping resources. Tags: [duplicates, trust but verify, finding things fast] [topics: config-push, clickhouse, rust, kill-switch]. Source: https://blog.cloudflare.com/18-november-2025-outage/

## Kubernetes and fleet operations

- **Datadog, 2023-03: auto-applied systemd update wipes Cilium routes in five regions** — An automatic security update restarted systemd-networkd on Ubuntu 22.04, which deleted the routes the Cilium CNI managed. Tens of thousands of nodes went offline within an hour. A legacy update channel's default 06:00 to 07:00 UTC window hit every region at the same moment, even though the regions are otherwise isolated. Full resolution took about 48 hours, with 450 to 750 responders. Fixes: they disabled the update channel, changed networkd to leave routes alone on restart, and added per-product status. Tags: [fan-out, partial failure] [topics: kubernetes, cilium, systemd, os-updates, multi-region]. Source: https://www.datadoghq.com/blog/2023-03-08-multiregion-infrastructure-connectivity-issue/
- **OpenAI, 2024-12: telemetry DaemonSet overloads Kubernetes API servers** — A new telemetry service made every node run expensive Kubernetes API calls whose cost grew with cluster size. That took down the control plane in most large clusters, and because DNS-based service discovery depended on the control plane, discovery failed too. Node DNS caches hid the failure for about 20 minutes, so the rollout kept going. All services were degraded or down for about 4h22m. Fixes: phased rollouts that watch control-plane health, break-glass API access, and service discovery decoupled from the control plane. Tags: [fan-out, overload, finding things fast] [topics: kubernetes, control-plane, dns, deploys]. Source: https://status.openai.com/incidents/ctrsv3lwd797

## Cloud region and facility outages

- **AWS, 2012-10: DNS gap plus a memory leak stalls EBS** — A DNS update for a replaced data-collection server did not reach every internal DNS server. EBS agents kept retrying the dead host and leaked memory, and per-process monitoring didn't exist to catch it. Volumes in one AZ stalled for about 6 hours. Heavy API throttling and an Elastic IP shortage stretched ELB recovery into the night. Fixes: per-process memory alarms, more reliable DNS propagation, a ban on aggressive throttling, and RDS failover bug fixes. Tags: [finding things fast, partial failure] [topics: ebs, dns, memory-leak, throttling]. Source: https://aws.amazon.com/message/680342/
- **AWS, 2017-02: mistyped command removes S3's index capacity** — An engineer meant to remove a few billing servers, but a typo removed far more, including capacity behind S3's index and placement subsystems. Both needed a full restart, which hadn't been done in large regions for years and was slow. S3 in us-east-1 was down for about 4h17m, taking dependent services with it. The status dashboard itself depended on S3 and could not be updated. Fixes: the tool removes capacity slowly and enforces minimum capacity, the index was split into cells sooner, and the dashboard became multi-region. Tags: [trust but verify, finding things fast] [topics: s3, operational-tooling, cells, us-east-1]. Source: https://aws.amazon.com/message/41926/
- **Google Cloud, 2019-06: maintenance automation deschedules the network control plane** — A maintenance event in one location made cluster automation deschedule network control-plane jobs in several locations, because of a bug in how it scoped them. The network ran fail-static for a few minutes, then BGP routes were withdrawn. Lost config had to be rebuilt. Several US regions lost connectivity for 3 to 4.5 hours, with Cloud Storage errors up to 96% in us-west2. Fixes: safeguards against descheduling across multiple locations, persisted control-plane config, and a longer fail-static period. Tags: [partial failure, fan-out] [topics: networking, automation, control-plane, bgp]. Source: https://status.cloud.google.com/incident/cloud-networking/19009
- **Slack, 2021-01: AWS Transit Gateway can't scale for the first Monday back** — After the holidays, cold client caches and a traffic surge overloaded an AWS Transit Gateway, causing packet loss. Web tiers saturated, and autoscaling tried to add 1,200 servers, which mostly failed because provisioning hit open-file and quota limits. Dashboards and alerting sat behind the same gateway and went dark. Slack was unavailable or degraded from about 7:00 to 10:40 PST. Fixes: pre-emptive gateway upscaling before holidays, monitoring placed with its databases, and load-tested provisioning. Tags: [overload, finding things fast] [topics: aws, transit-gateway, autoscaling, observability]. Source: https://slack.engineering/slacks-outage-on-january-4th-2021/
- **Cloudflare, 2023-11: power loss at one facility exposes hidden single-site dependencies** — The PDX-04 facility lost utility power and generators to a ground fault, and its UPS ran out after about 4 minutes. Cloudflare's control plane was designed to survive losing a facility, but some services secretly depended on Kafka and ClickHouse running only there, and a full-facility test had never been run. Control plane and analytics were affected for about 40 hours, and some log-push data was lost for good. The "Code Orange" response requires GA products to use the HA cluster, adds full-facility removal tests, and makes analytics able to fail over. Tags: [partial failure, trust but verify] [topics: disaster-recovery, kafka, clickhouse, data-centers]. Source: https://blog.cloudflare.com/post-mortem-on-cloudflare-control-plane-and-analytics-outage/

## Observability, backups and verification failures

- **Sentry, 2015-07: Postgres transaction ID wraparound halts writes** — Autovacuum fell behind on a huge table, and Postgres reached its transaction ID limit and stopped accepting writes to avoid corruption. Sentry was read-only for most of a US workday, with event queues and Redis buffers growing. Truncating the offending table brought writes back within minutes. Fixes: new hardware, retuned autovacuum (lower freeze age, more workers, no cost delay), and plans to split data across databases. Tags: [finding things fast, overload] [topics: postgres, vacuum, wraparound, queues]. Source: https://blog.sentry.io/transaction-id-wraparound-in-postgres/
- **GitLab, 2017-01: wrong-host rm -rf, with backups that had never worked** — Spam load caused replication lag, so the replica had to be rebuilt. During the rebuild an engineer deleted about 300GB on the primary instead of the replica. The pg_dump backups had been failing silently because of a version mismatch, and their alert emails were rejected over DMARC. Recovery used a 6-hour-old staging snapshot, with about 18 hours of downtime and data lost for about 5,000 projects. Fixes: hourly snapshots, automated restore tests, WAL archiving, backup monitoring, and a named owner for data durability. Tags: [trust but verify, finding things fast] [topics: postgres, backups, replication, alerting]. Source: https://about.gitlab.com/blog/2017/02/10/postmortem-of-database-outage-of-january-31/
- **Atlassian, 2022-04: deletion script given site IDs instead of app IDs** — A cleanup script was meant to delete a legacy app, but because of a handoff gap it was given site IDs. The API accepted either kind of ID without checking. In about 23 minutes it deleted 883 sites belonging to 775 customers. ## Consistency, CAP and membership (appended during the sd-020 lesson upgrade, October 2026)

- **Jepsen (MongoDB 3.6.4), 2018-10: causal sessions break with sub-majority concerns** — MongoDB documents read-your-writes, monotonic reads, monotonic writes and writes-follow-reads for causal sessions. Guarantees held only with `majority` reads and writes. MongoDB closed SERVER-35316 as working as designed and documented the majority requirement (September 2018). - **Facebook, 2015-10: measuring anomalies under eventual consistency in TAO (SOSP paper)** — A 12-day trace (20 to 31 August 2015) of every request to 1 in a million objects, over 2.7 billion requests, was checked against stronger models. Tags: [trust but verify, ordering] [topics: tao, eventual-consistency, linearizability, monitoring]. Source: https://www.cs.princeton.edu/~wlloyd/papers/existential-sosp15.pdf
- **Google, 2017: Spanner incident data and the "effectively CA" claim (Brewer)** — Brewer calls Spanner technically CP but effectively CA, meaning five or more nines with few outages caused by partitions. The two biggest outages were software bugs hitting all replicas of a database at once. Chubby's geo-distributed cells averaged 99.99958% availability for 30s+ outages. - **HashiCorp, 2017-07: Lifeguard cuts SWIM false positives (engineering write-up)** — In memberlist (used by Consul and Serf), slow message processing from CPU exhaustion, network delay or loss made healthy members look failed, diverting traffic and triggering needless rebalancing. - **Amazon, 2007: Dynamo makes permanent membership explicit and gossips only the history (SOSP paper)** — Because outages are usually transient and human error can start nodes by accident, ring joins and removals are admin commands persisted with their time; gossip with one random peer per second reconciles the histories. - **Apache Kafka, KIP-101 (design write-up): leader epochs replace high-watermark truncation** — Followers truncated to a high watermark they learn one fetch late, so a restart plus leader change could lose committed messages, and after a power outage replicas could diverge. ## Dispatch, location and ETA (appended during the sdi-043 lesson upgrade, October 2026)

- **DoorDash, 2022-05: database resize latency trips default Envoy circuit breakers platform-wide** — At 9:40 am on 12 May a routine downsizing of the delivery service's distributed database began; p99 latency alerts at 10:29, 11:30 and 2:45 were tolerated because the SLO held. ## Scarce inventory, auctions and exchanges (appended during the sdi-049 lesson upgrade, October 2026)
