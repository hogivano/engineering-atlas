# Incident catalogue: security, identity, supply chain, payments, AI and real-time apps

Real, publicly documented incidents and engineering write-ups. Every entry links a primary source (the company's own postmortem, status page, security bulletin or engineering blog, an official regulator order, or a paper). Each source URL was opened and the details below were checked against it in October 2026. Candidates whose primary source could not be opened or confirmed (for example OpenAI's March 2023 ChatGPT Redis write-up, Epic's 2018 Fortnite postmortem and X/Twitter's 2018 and 2020 security posts, all of which return 403 to automated fetches) were left out.

Tag vocabulary for problem shapes: contention, duplicates, ordering, fan-out, hot spots, overload, partial failure, multi-step consistency, finding things fast, trust but verify.

## Auth, identity and SSO

- **Facebook, 2018-09: "View As" bug minted other people's access tokens**: Three bugs combined. Inside the View As preview, a birthday composer wrongly offered video upload, and the video uploader (added July 2017) generated a mobile-app access token for the profile being *viewed* rather than for the viewer. The token appeared in the page HTML, so attackers could harvest it and pivot from account to account. About 50M accounts were affected, tokens were reset for another 40M as a precaution, and about 90M people had to log in again. Facebook fixed the bug, reset tokens and turned View As off until a security review was finished (it came back in May 2019). Tags: [trust but verify, multi-step consistency, fan-out] [topics: access tokens, session management, authorization]. Source: https://about.fb.com/news/2018/09/security-update/

- **Meta, 2019-03: passwords found in readable form in internal logs**: A routine security review in January 2019 found that some user passwords had been written in plaintext to internal storage, even though the login path was designed to mask them. The estimate was hundreds of millions of Facebook Lite users, tens of millions of other Facebook users and, after an April update, millions of Instagram users. Meta fixed the logging, notified everyone affected, reviewed how other secrets such as access tokens were stored, and pushed users toward 2FA and security keys. Tags: [trust but verify, finding things fast] [topics: logging, password handling, secrets hygiene]. Source: https://about.fb.com/news/2019/03/keeping-passwords-secure/

- **Google, 2020-12: identity service lost its quota and every Google login failed**: An automated quota system migration wrongly saw the User ID Service's usage as zero. When a grace period ran out, the automation cut the service's storage quota, and its Paxos leader could no longer write to the account database. Reads went stale and authentication lookups failed. For 47 minutes (03:46–04:33 PT) credential issuance failed for all Google user accounts, Workspace was down, and Cloud APIs that needed OAuth returned 5xx (GCS about 15%, BigQuery streaming about 75%). Engineers turned off quota enforcement. Follow-ups included guarding quota automation against fast global cuts and making the identity database more resilient to write failures. Tags: [trust but verify, partial failure, hot spots] [topics: authentication, quotas, paxos, automation safety]. Source: https://status.cloud.google.com/incident/zall/20013

- **Cloudflare, 2022-07: hardware keys stopped a real-time SMS phishing kit**: At least 76 employees and some family members got texts within about a minute, linking to a lookalike Okta page on a domain registered under 40 minutes earlier. The page sent each username, password and TOTP code to the attacker over Telegram as it was typed, so the codes could be replayed before they expired. Three employees entered credentials, but logins failed because every employee uses origin-bound FIDO2 keys rather than TOTP. Cloudflare added sandboxing for newly registered domains, browser isolation for SSO-themed lookalike sites and blocks on logins from residential proxies and unknown VPNs. Tags: [trust but verify] [topics: phishing, mfa, fido2, webauthn, okta]. Source: https://blog.cloudflare.com/2022-07-sms-phishing-attacks/

- **Twilio, 2022-08: SMS phishing led to access to internal admin tools**: Current and former employees got texts posing as IT, saying their password had expired and linking to fake Okta login pages. Employees who entered credentials gave the attackers access to internal admin tooling. The final count was 209 customers (of more than 270,000) and 93 Authy end users affected, with unauthorized activity ending on August 9. Twilio gave FIDO2 tokens to every employee, tightened VPN access, cut back admin tool features and refreshed Okta app tokens more often. Tags: [trust but verify, fan-out] [topics: phishing, mfa, insider tooling, least privilege]. Source: https://www.twilio.com/en-us/blog/august-2022-social-engineering-attack

- **Dropbox, 2022-10: phish impersonating CircleCI captured GitHub credentials and OTPs**: Employees landed on a fake CircleCI login page, typed in their GitHub password and then passed a one-time code from their hardware key to the attacker's site. The attacker copied 130 repositories that held some developer API keys and a few thousand names and email addresses. Dropbox's core app code was not taken. GitHub flagged the activity on October 14 and access was cut that day. Dropbox rotated the exposed keys and sped up its move to phishing-resistant WebAuthn. Tags: [trust but verify] [topics: phishing, otp, webauthn, source code secrets]. Source: https://dropbox.tech/security/a-recent-phishing-campaign-targeting-dropbox

- **Okta, 2023-10: support system breach through HAR files that held session tokens**: An attacker used a support service account whose password an employee had saved in a personal Google profile signed in to Chrome on a work laptop. Customers had uploaded HAR files to support cases, and those files contained live session tokens, which the attacker used to hijack sessions. Files from 134 customers (under 1% of Okta's customers) were accessed and 5 customers had sessions hijacked (1Password, BeyondTrust and Cloudflare among those targeted). Detection took about 14 days, partly because viewing a file through a case writes a different log event than opening it from the Files tab. Okta disabled the account, blocked personal Chrome profiles on managed laptops and shipped session binding to network location for admins. Tags: [trust but verify, finding things fast] [topics: session tokens, har files, support tooling, logging]. Source: https://sec.okta.com/articles/2023/11/unauthorized-access-oktas-support-case-management-system-root-cause

- **Microsoft, 2023-07: Storm-0558 forged Exchange tokens with a consumer signing key**: A China-based actor used a Microsoft account (MSA) consumer signing key to forge tokens that enterprise Outlook/Exchange accepted. Microsoft's most likely explanation was a key that reached a debugging environment through a 2021 crash dump and was taken from a compromised engineer account. A 2024 addendum said no dump containing the key had actually been found. The access only worked because Microsoft's validation libraries checked signatures but not key scope, and the mail system's developers assumed they did both, so a consumer key was accepted for enterprise mail. Microsoft fixed the crash-dump handling, improved credential scanning and shipped libraries that check key scope automatically. Tags: [trust but verify, multi-step consistency] [topics: jwt, token validation, key management, crash dumps]. Source: https://www.microsoft.com/en-us/msrc/blog/2023/09/results-of-major-technical-investigations-for-storm-0558-key-acquisition

- **Cloudflare, 2025-06: Workers KV outage made Access fail closed and blocked every SSO login**: A third-party cloud storage provider behind Workers KV went down, and KV request failures peaked at about 90%. Because Access, WARP, Gateway and the dashboard login all read identity and policy data from KV, 100% of identity-based Access logins failed for about 2.5 hours (17:52–20:28 UTC). Access fails closed by design, so it denied rather than allowed. Turnstile's kill switch let traffic through but allowed tokens to be redeemed twice. Cloudflare is cutting KV's dependence on any single store (moving to R2) and building tooling to re-enable namespaces gradually so cold caches aren't overwhelmed. Tags: [partial failure, fan-out, overload, duplicates] [topics: sso, fail-closed vs fail-open, dependencies, kv store]. Source: https://blog.cloudflare.com/cloudflare-service-outage-june-12-2025/

- **Google Cloud, 2025-06: one blank policy row crashed API authorization worldwide**: A quota policy written to globally replicated Spanner tables had blank fields. Service Control, which runs policy and quota checks on every API call, hit a null pointer in a code path added May 29 that had no feature flag and no error handling, and crash-looped in every region within seconds. External APIs returned 503 for hours, with residual impact until 18:18 PT (start 10:51 PT). A "red button" shut off the bad path in about 40 minutes, but restarting tasks hammered Spanner in us-central1 because there was no randomized backoff. Google plans to make checks fail open, propagate global data incrementally, put critical code behind feature flags that default to off, and add backoff everywhere. Tags: [fan-out, overload, partial failure, trust but verify] [topics: authorization, config push, feature flags, retries, backoff]. Source: https://status.cloud.google.com/incidents/ow5i3PPK96RduMcb1SsW

## Secrets leaks and stolen tokens

- **Cloudflare, 2017-02: "Cloudbleed" parser bug leaked memory into responses**: A bug in the error handling of a Ragel-generated HTML parser let the pointer run past the end of a buffer when a page ended in an unclosed tag. The end check used equality, so the overrun went unnoticed. Moving features to a new parser changed buffer handling and made the bug reachable. At the peak, about 1 in 3.3M requests leaked memory (cookies, auth headers, POST bodies, OAuth tokens). 770 URIs across 161 domains turned up in search engine caches. Google reported it on 2017-02-18. Cloudflare had a mitigation out in 47 minutes and a full fix in under 7 hours, added bounds checks on every pointer access and started fuzzing older code. Tags: [finding things fast, trust but verify] [topics: memory safety, parsers, kill switches, cache purge]. Source: https://blog.cloudflare.com/incident-report-on-memory-leak-caused-by-cloudflare-parser-bug/

- **Heroku, 2022-04: stolen machine token led to the theft of customers' GitHub OAuth tokens**: An attacker got a token for a Heroku machine account (via an archived private repo they reached through a third-party integration). They used it on April 7 to download customers' GitHub integration OAuth tokens, hashed passwords and later pipeline config vars, then used those tokens to enumerate and clone private repos. GitHub detected this through npm's infrastructure, and Heroku revoked every Dashboard GitHub token, blocked new ones for weeks and reset all customer passwords. It also froze production changes, re-encrypted data and cut back token permissions and database access. Tags: [trust but verify, fan-out] [topics: oauth, token storage, third-party integrations, password reset]. Source: https://www.heroku.com/blog/april-2022-incident-review

- **GitHub, 2022-04: OAuth tokens stolen from Heroku and Travis CI used to clone private repos**: GitHub found an attacker calling its API with OAuth user tokens issued to the Heroku Dashboard and Travis CI apps. The attacker listed victims' orgs and private repos and cloned some, including npm's, and got an AWS key from them. GitHub said the tokens weren't stolen from GitHub, since it doesn't store them in usable form. It revoked its own and npm's tokens, asked Heroku and Travis CI to revoke theirs, and notified dozens of victim organizations between April 15 and 27. Tags: [trust but verify, fan-out, finding things fast] [topics: oauth, api tokens, secrets in repos]. Source: https://github.blog/2022-04-15-security-alert-stolen-oauth-user-tokens/

- **Slack, 2022-12: stolen employee tokens used to download private GitHub repos**: A small number of Slack employee tokens, stolen through a compromised third-party vendor, were used on December 27 to download private repos from Slack's externally hosted GitHub. Slack was alerted on December 29. The repos did not include the main codebase or customer data. Slack invalidated the tokens, rotated credentials, added alerting on that GitHub organization and worked on storing repo access tokens more safely. Tags: [trust but verify] [topics: tokens, vendor risk, source code]. Source: https://slack.com/blog/news/slack-security-update

- **CircleCI, 2023-01: malware stole a 2FA-backed SSO session and customer secrets were exfiltrated**: Malware that antivirus missed stole an engineer's SSO session cookie on December 16, 2022. The session was already 2FA-authenticated, so the attacker could act as the engineer, create production access tokens and pull encryption keys from a running process. That made the encrypted customer environment variables and tokens readable. Data was taken on December 22, and a customer report of odd GitHub OAuth activity led to discovery on December 29. CircleCI told every customer to rotate all secrets on January 4, cut production access to a small group, added step-up auth and planned OIDC, GitHub Apps and automatic token rotation. Tags: [trust but verify, finding things fast] [topics: session cookies, secrets management, ci/cd, encryption keys]. Source: https://circleci.com/blog/jan-4-2023-incident-report/

- **GitHub, 2023-03: RSA SSH host private key briefly exposed in a public repo**: GitHub.com's RSA SSH host private key was accidentally published in a public GitHub repository. GitHub replaced the key at about 05:00 UTC on March 24, and the change propagated in about 30 minutes. Everyone using RSA for Git over SSH then got a host key mismatch warning and had to update known_hosts, and Actions workflows pinned to an old actions/checkout SHA with ssh-key broke. GitHub saw no evidence of abuse. Tags: [trust but verify] [topics: ssh, host keys, key rotation, secrets in repos]. Source: https://github.blog/2023-03-23-we-updated-our-rsa-ssh-host-key/

- **Microsoft, 2023-06: overly broad Azure SAS token published with open-source AI training material**: A Microsoft AI researcher put a blob storage URL containing a SAS token in a public GitHub repo for open-source AI models. Wiz used the token to open the storage account, which held workstation backups and Teams messages of two former employees. Wiz reported it on June 22 and Microsoft revoked the token on June 24. A scanner had wrongly marked the URL as benign. Microsoft fixed that false positive, extended GitHub secret scanning to flag SAS tokens with long expiry or broad permissions, rescanned its public repos and recommends SAS lifetimes of one hour or less. Tags: [trust but verify, finding things fast] [topics: sas tokens, secret scanning, ai datasets, least privilege]. Source: https://www.microsoft.com/en-us/msrc/blog/2023/09/microsoft-mitigated-exposure-of-internal-information-in-a-storage-account-due-to-overly-permissive-sas-token

- **Cloudflare, 2023-11: credentials missed in post-Okta rotation used to breach Atlassian**: After the October 2023 Okta breach, Cloudflare rotated credentials but skipped four (one service token and three service accounts) that it wrongly believed were unused. An attacker used them from November 14, got into Jira, Confluence and Bitbucket, installed the Sliver C2 framework and downloaded 76 repos before being detected on November 23. Cloudflare reports no customer impact. Its "Code Red" response rotated more than 5,000 production credentials, triaged 4,893 systems, reimaged every machine in its global network and replaced hardware at a São Paulo data center that wasn't yet live. Tags: [trust but verify, finding things fast] [topics: credential rotation, service accounts, okta, incident response]. Source: https://blog.cloudflare.com/thanksgiving-2023-security-incident/

- **Snowflake customers, 2024-05: infostealer credentials without MFA used for mass data theft**: Mandiant tracked UNC5537 logging in to Snowflake customer instances with usernames and passwords harvested by infostealer malware, some taken as far back as 2020 and never rotated. At least 79.7% of the accounts used had prior exposure, none required MFA and none had network allow lists. About 165 organizations were notified, and Mandiant found no breach of Snowflake's own corporate environment. The advice was MFA everywhere, credential rotation, IP allow lists and alerts on bulk COPY INTO and stage creation. Tags: [trust but verify, finding things fast] [topics: credential stuffing, mfa, data warehouse, infostealers]. Source: https://cloud.google.com/blog/topics/threat-intelligence/unc5537-snowflake-data-theft-extortion

- **Hugging Face, 2024-05: unauthorized access to Spaces secrets**: Hugging Face detected unauthorized access to secrets stored for Spaces (hosted ML apps) and suspected some had been read. It revoked HF tokens found in those secrets, emailed affected users, removed org tokens, moved Spaces secrets to a KMS and made fine-grained tokens the default, with plans to retire classic read/write tokens. Tags: [trust but verify] [topics: secrets storage, kms, api tokens, ml platforms]. Source: https://huggingface.co/blog/space-secrets-disclosure

- **Salesloft Drift, 2025-08: stolen OAuth tokens for a chat-bot integration used to mine Salesforce for secrets**: Between August 8 and 18, actor UNC6395 used stolen OAuth tokens for the Salesloft Drift app to run SOQL queries that exported Account, User, Opportunity and Case records from many companies' Salesforce instances. They then searched the data for AWS keys (AKIA), passwords and Snowflake tokens. Salesloft and Salesforce revoked all Drift tokens on August 20, Salesforce pulled the app from AppExchange, and Google later found that Drift Email tokens had reached a few Workspace accounts. Tags: [trust but verify, fan-out] [topics: oauth, saas integrations, secrets in tickets, token revocation]. Source: https://cloud.google.com/blog/topics/threat-intelligence/data-theft-salesforce-instances-via-salesloft-drift

## Supply chain

- **npm, 2016-03: left-pad unpublish broke thousands of builds**: In a naming dispute, a maintainer unpublished 273 packages, including the tiny left-pad, and thousands of projects that depended on it directly or indirectly failed to install. A republished 1.0.0 didn't satisfy pins on 0.0.3, so npm restored the original from backup. Breakage lasted about 2.5 hours. npm then limited unpublishing of packages that others depend on and started holding the names of removed packages with placeholders. Tags: [fan-out, partial failure] [topics: package registry, dependency pinning, immutability]. Source: https://blog.npmjs.org/post/141577284765/kik-left-pad-and-npm

- **npm, 2018-11: event-stream maintainer handover used to steal from a bitcoin wallet**: An attacker talked their way into maintaining event-stream and added the malicious flatmap-stream as a dependency in 3.3.6 (September 2018). The payload only ran inside the Copay wallet's build and tried to steal keys from wallets holding more than 100 BTC or 1,000 BCH. Copay 5.0.2–5.1.0 shipped the code. npm removed the package versions, took ownership of event-stream and told users to run npm audit. Tags: [trust but verify] [topics: maintainer takeover, dependencies, crypto wallets]. Source: https://blog.npmjs.org/post/180565383195/details-about-the-event-stream-incident

- **Codecov, 2021-04: tampered Bash Uploader sent CI environment variables to an attacker**: A mistake in how Codecov built its Docker images exposed a storage credential. From January 31 an attacker used it to add one curl line to the uploader script that sent each CI runner's environment (tokens, keys) and git remote to a remote server. This went on for about two months (108 distinct windows) until a customer's checksum check failed on April 1. Codecov rotated keys, added monitoring and told customers to rotate every secret their CI exposed and to verify uploader checksums. Tags: [trust but verify, finding things fast, fan-out] [topics: ci/cd, curl-pipe-bash, checksums, secrets]. Source: https://about.codecov.io/security-update/

- **PyTorch, 2022-12: dependency confusion through torchtriton on PyPI**: Someone uploaded a package named torchtriton to PyPI, matching the name of a dependency PyTorch nightly fetched from its own index. pip preferred PyPI, so Linux nightly installs from December 25–30 pulled the malicious version. Its binary collected hostname, environment, /etc/passwd, ~/.ssh and up to 1,000 home-directory files and sent them out over encrypted DNS queries. PyTorch renamed the dependency to pytorch-triton, registered a placeholder on PyPI and removed the affected nightlies. Tags: [trust but verify] [topics: dependency confusion, package index precedence, dns exfiltration]. Source: https://pytorch.org/blog/compromised-nightly-dependency/

- **xz Utils, 2024-03: backdoor in a compression library targeted sshd**: Andres Freund noticed sshd logins using extra CPU (about 0.5 s versus 0.01 s in one test) and valgrind errors, and traced them to liblzma 5.6.0/5.6.1. Obfuscated payloads were hidden in test files and pulled in by a build-to-host.m4 line that appeared only in the release tarballs, not in git. The code hooked the IFUNC resolvers and redirected RSA_public_decrypt in sshd, reachable because distro systemd patches link sshd to liblzma. It became CVE-2024-3094 and was caught before most stable distros shipped it. Tags: [trust but verify, finding things fast] [topics: open source maintainers, reproducible builds, ssh, performance regressions]. Source: https://www.openwall.com/lists/oss-security/2024/03/29/4

- **tj-actions/changed-files, 2025-03: retargeted tags dumped CI secrets into public logs**: Attackers moved existing version tags of a GitHub Action used by more than 23,000 repos to a malicious commit. The code read secrets from the runner worker's memory and printed them base64-encoded into workflow logs, which anyone can read on public repos. Exposure ran March 14–15. StepSecurity spotted an unexpected call to gist.githubusercontent.com. Tracked as CVE-2025-30066, it was fixed in 46.0.1, and users were told to rotate secrets and pin actions to full commit SHAs. Tags: [trust but verify, fan-out] [topics: github actions, mutable tags, ci secrets]. Source: https://github.com/advisories/GHSA-mrrh-fwg8-r2c3

- **AWS, 2025-07: over-scoped CI token let malicious code ship in Amazon Q Developer extension**: A GitHub token in the CodeBuild configuration had more access than it needed. An attacker used it to commit malicious code to the Amazon Q Developer VS Code extension repo, and the release pipeline shipped it in version 1.84.0 (CVE-2025-8217). AWS says a syntax error kept the code from running. AWS revoked the credentials, released 1.85.0 and pulled 1.84.0 from distribution. Tags: [trust but verify] [topics: ci/cd tokens, least privilege, ai coding assistants, release pipeline]. Source: https://aws.amazon.com/security/security-bulletins/AWS-2025-015/

- **Nx, 2025-08: workflow injection stole the npm token, and the payload tried to turn AI CLIs into secret hunters**: A new GitHub Actions workflow on pull_request_target put PR titles straight into a shell step, and old branches still had it after it was removed from master. An attacker used it to run publish.yml and send the npm token to a webhook. Malicious nx versions went out on August 26 (for about 4 hours on npm). Their postinstall script collected credentials (its prompt told local AI agents to list secret files), posted them to a public "s1ngularity-repository" in each victim's GitHub account and appended a shutdown command to shell rc files. Nx moved to npm Trusted Publishing, required 2FA, purged the workflow from all branches and requires approval for workflows from outside contributors. Tags: [trust but verify, fan-out] [topics: github actions, script injection, npm, ai agents]. Source: https://github.com/nrwl/nx/security/advisories/GHSA-cxm3-wv7p-598c

## Payments and money

- **Knight Capital, 2012-08: half-finished deploy woke dead trading code and lost $460M in 45 minutes**: New code for a retail liquidity program reused a flag that used to turn on "Power Peg," trading logic that hadn't been used since 2003. A technician deployed the code to only 7 of 8 servers. On the eighth server the flag ran Power Peg, which no longer tracked filled quantity and so kept sending child orders. It made 4M executions in 154 stocks in about 45 minutes, leaving roughly $3.5B net long and causing a $460M loss. During the response, staff removed the new code from the 7 good servers, which made all 8 run Power Peg. The SEC fined Knight $12M and cited missing deployment review and incident procedures. Tags: [partial failure, duplicates, trust but verify] [topics: deployment, feature flags, dead code, kill switches]. Source: https://www.sec.gov/litigation/admin/2013/34-70694.pdf

- **Stripe, 2017-02: designing APIs for safe retries with idempotency keys (engineering write-up)**: Stripe explains why a charge must happen exactly once even when a network failure leaves it unclear whether the request arrived, half-completed or succeeded with the response lost. Clients send a unique Idempotency-Key with each POST. The server replays the stored result or resumes the operation, and clients retry with exponential backoff plus jitter so a recovering server isn't hit by a thundering herd. Stripe's client libraries do this automatically. Tags: [duplicates, overload, multi-step consistency] [topics: idempotency, retries, backoff, jitter, payments api]. Source: https://stripe.com/blog/idempotency

- **Stripe, 2019-07: database failover bug and a bad rollback took down most API requests**: A database minor version deployed three months earlier had a latent failover bug that only appeared when several nodes stalled. When a shard's primary failed, the shard couldn't elect a new one and stopped accepting writes. Shared resources then ran out and the API failed (16:35–17:02 UTC). The fix was a rollback of the election protocol, but it interacted with a new configuration setting, starved CPU and caused a second outage (21:14–22:47). A large majority of API requests failed in both windows. Stripe added monitoring for stalled replication, circuit breakers per cluster and limits on client retries, and planned safer config-change tooling. Tags: [partial failure, overload, fan-out] [topics: database failover, leader election, rollbacks, circuit breakers]. Source: https://stripe.com/rcas/2019-07-10

## AI, LLMs and agents

- **Greshake et al., 2023-02: indirect prompt injection against real LLM-integrated apps (paper)**: The paper shows that an attacker doesn't need to talk to the model directly. Instructions hidden in a web page, email or code file that an app later retrieves can take over the app, because these systems "blur the line between data and instructions." The authors demonstrated data theft, worm-like spread and manipulated answers against Bing's GPT-4 chat and code-completion tools. It is the reference that defines the attack class behind most later agent incidents. Tags: [trust but verify] [topics: prompt injection, llm security, retrieval-augmented generation, agents]. Source: https://arxiv.org/abs/2302.12173

- **Anthropic, 2025-08/09: three infrastructure bugs quietly degraded Claude's answers**: Three separate bugs overlapped. (1) Some Sonnet 4 requests were routed to servers configured for the coming 1M-token context, and sticky routing kept users there: 0.8% of requests at first, 16% at the worst hour, and about 30% of Claude Code users hit at least once. (2) A TPU misconfiguration occasionally gave high probability to wildly unlikely tokens, such as Thai text in English replies. (3) A latent XLA compiler bug in approximate top-k sometimes dropped the most likely token. The issues were hard to see because evals didn't catch them and they depended on load and batch size. Anthropic fixed the routing, switched to exact fp32 top-k and added production quality monitoring and more sensitive evals. Tags: [finding things fast, partial failure, trust but verify] [topics: llm serving, load balancing, compilers, evals]. Source: https://www.anthropic.com/engineering/a-postmortem-of-three-recent-issues

- **Anthropic, 2025-09: AI coding agent turned into a largely autonomous espionage operator**: A group Anthropic assessed as Chinese state-sponsored jailbroke Claude Code by breaking the attack into small, innocent-looking tasks and claiming to be a security firm doing defensive testing. It then aimed the agent at about 30 targets in tech, finance, chemicals and government, and a few intrusions succeeded. The AI did about 80–90% of the work, with humans stepping in at roughly 4–6 decision points per campaign and peak rates of several requests per second. Anthropic banned the accounts within about ten days, notified victims and built better classifiers. Tags: [trust but verify, finding things fast] [topics: ai agents, jailbreaks, misuse detection, abuse monitoring]. Source: https://www.anthropic.com/news/disrupting-AI-espionage

## Real-time apps (chat, video, games)

- **Pokémon GO / Google Cloud, 2016-07: launch traffic hit 50 times the planned target**: Niantic planned for 1x traffic with 5x as the worst case, but player traffic reached 50x, measured through Cloud Datastore load. Google's reliability engineers added tens of thousands of cores. Before the Japan launch, Niantic upgraded GKE to a version that allowed 1,000+ more nodes and moved from the network load balancer to the HTTP/S load balancer, both without taking players offline. Japan then launched without a major incident. Tags: [overload, hot spots] [topics: capacity planning, kubernetes, load balancers, launch readiness]. Source: https://cloud.google.com/blog/products/gcp/bringing-pokemon-go-to-life-on-google-cloud

- **Discord, 2017-11: cloud network blips cascaded through Erlang session services**: A Google Cloud networking change caused brief network drops on Discord's VMs. The busy sessions cluster suffered 16 drops, and the Erlang services overloaded and got stuck, made worse by an unreliable HTTP library and slow service discovery. There were two full outages of about 30 minutes each and 14 partial ones over about 24 hours, and each full restart forced millions of clients to reconnect. Google rolled back the change, and Discord fixed the net_kernel overload, replaced the HTTP library and service discovery components and expanded load testing. Tags: [partial failure, overload, fan-out] [topics: erlang, websockets, reconnect storms, service discovery]. Source: https://discordstatus.com/incidents/mpzkz7m4fzpt

- **Slack, 2021-01: post-holiday traffic overloaded AWS Transit Gateways and autoscaling made it worse**: On the first workday of 2021, clients with cold caches drove a traffic jump that AWS Transit Gateways couldn't scale for fast enough. Packet loss made health checks fail, so autoscaling removed instances and tried to add about 1,200. The provisioning service hit its open-file limit and an AWS quota, and dashboards failed because they reached their databases across the same gateways. Slack was down from about 7:00 to 9:15 PT and degraded until 10:40. Fixes included pre-scaling the gateways, putting monitoring in the same VPC as its databases, load testing the provisioning service and revisiting health-check and autoscaling rules. Tags: [overload, partial failure, fan-out] [topics: autoscaling, health checks, aws networking, observability]. Source: https://slack.engineering/slacks-outage-on-january-4th-2021/

- **Meta, 2021-10: backbone command and BGP withdrawal took every Meta app offline**: A maintenance command meant to check backbone capacity instead cut every backbone link, and the audit tool that should have blocked it had a bug. With no route to the data centers, Meta's DNS servers concluded they were unhealthy and withdrew their BGP routes, so Facebook, Instagram and WhatsApp disappeared from the internet. Engineers had to go on site because remote access and internal tools also depended on DNS. Services were brought back gradually so tens of megawatts of returning load wouldn't overwhelm power systems and caches. - **CERT/CC and Duo, 2018-02: XML comments let attackers split identities in SAML libraries**: Several SAML libraries read a node's text in a way that stopped at an XML comment, while canonicalisation removed comments before signing, so text after a comment was not covered by what the library read. Source: https://httpd.apache.org/security/vulnerabilities_24.html

- **jackson-databind, 2022-03: deeply nested JSON causes a stack overflow (CVE-2020-36518)** — Recursive deserialisation of very deeply nested input threw a Java StackOverflowError, a denial-of-service vector. Fixed in 2.12.6.1 and 2.13.2.1; Jackson 2.15 later added StreamReadConstraints with a default maximum nesting depth of 1000. Tags: [overload, trust but verify] [topics: json, recursion, denial-of-service]. Source: https://github.com/advisories/GHSA-57j2-w4cx-62h2

- **Quarkus REST, 2025: CVE-2025-1247 request parameters leak between concurrent requests** — Endpoints using field injection without a CDI scope were shared across requests, so under concurrency one user's request data could be exposed to another (CWE-488, CVSS 8.3). Tags: [contention, trust but verify] [topics: shared-mutable-state, singleton-scope, request-context]. Source: https://access.redhat.com/security/cve/cve-2025-1247
